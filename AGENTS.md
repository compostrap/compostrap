# compostrap

One npm package for Bootstrap 5.3, independent of Nette and drago (drago packages use it, it never refers to them), for administrations and websites. It replaces the separate packages `theme-switcher-compostrap`, `sidebar-skeleton-compostrap`, `sidebar-menu-compostrap`, `sidebar-menu-2-compostrap` and `dashboard-skeleton-compostrap`; the pill look of `sidebar-menu-2` is part of `sidebar-menu` (`_pills.scss`), there is no flat menu.

## Architecture

Three layers; keep every new piece in the layer it belongs to:

| Layer | Modules | What belongs there |
|-------|---------|--------------------|
| Theme | `theme` | Bootstrap itself: its variables (`theme/_variables.scss`) and CSS that changes its components, plus the classes of Bootstrap 6 backported with their names (`theme-*` tokens, `btn-subtle`, `badge-subtle`, `breadcrumb-link`, `avatar`, `btn-xs`, `btn-icon`, `form-adorn`, `form-ghost`…). No own class names, except size modifiers in the naming of Bootstrap (`badge-sm`, `form-check-sm`) and `btn-group-segmented` (the look of `btn-group[role=tablist]` for any group). |
| Layout | `sidebar`, `sidebar-menu`, `dashboard` | the frame of an administration: sidebar, menu, navbar over the content (`navbar-*`), content boxes (`content-box`), page colors (`--ds-*`), nanobar. |
| Components | `theme-switcher`, `tooltip`, `elements`, `dialogs`, `settings`, `datagrid`, `selection`, `sortable`, `number-input`, `otp-input`, `datepicker`, `rating`, `chart`, `gallery`, `dropzone`, `lightbox`, `strength`, `password-toggle`, `empty`, `spinner`, `auth`, `shop`, `blog` | everything with an own name; the class prefix is the module or its part (`gallery-*`, `empty-*`, `auth-*`, `shop-*`, `blog-*`, `stat-*`, `setting-*`, `datagrid-*`, `selection-*`, `otp-*`, `sortable-*`). |

Where new code goes:
- It changes or completes a class of Bootstrap 5 or 6 → the theme, into the partial of that component (`theme/_buttons.scss`, `_badges`, `_alerts`, `_forms`, `_navs`, `_breadcrumb`, `_tables`, `_cards`, `_accordion`, `_overlays`, `_avatar`; colors and the `--theme-*` tokens in `_colors`, the page in `_base`). A new component of Bootstrap gets its own partial, imported in `theme/_index.scss`.
- It has an own name → a component module. A small piece of a page goes to `elements` (as its own partial), a piece of modals/offcanvas/toasts to `dialogs`, a section list or a setting row to `settings`; a bigger thing with its own markup or JavaScript gets a new module.
- It is a part of the frame of the administration → `sidebar`, `sidebar-menu` or `dashboard`.
- A component never goes into `dashboard` because it is first used on the dashboard; `dashboard` holds only the frame.

A new module:
1. `src/scss/<module>/_index.scss` (with partials for its parts) and the entry point `src/scss/<module>.scss` (`@use '<module>/index';`).
2. Load it in `src/scss/compostrap.scss` and list it in `scripts/build-css.js`, both in the module order below.
3. JavaScript (when it has any): `src/js/<module>.js`, export it in `src/js/index.js`, an entry in `vite.config.js` and in `exports` of `package.json` (`compostrap/<module>`).
4. A demo page (or a section of one) in `demo/pages/` and its item in the menu of `scripts/build-demo.js`.
5. Its description in `docs/<module>.md` (a part of the theme in `docs/theme.md`, of the frame in `docs/layout.md`), a row in the module table of `readme.md` with a link to it and its link in the Documentation list there. `readme.md` holds only the overview (requirements, installation, architecture, usage, light and dark theme, demo, tests); the markup, classes, variables and JavaScript of a module are described in `docs/`, one file per component.

## Files

- `src/scss/_bootstrap.scss`: the only place that loads Bootstrap (functions, variables, mixins) by `@import`, because Bootstrap 5.3 has no Sass modules, with `theme/_variables.scss` first; modules use it as `@use '../bootstrap' as bs;`. Everything else uses `@use`.
- `theme` is the exception among modules: `theme.scss` builds Bootstrap itself (`theme/_variables.scss` = Bootstrap variables with `!default`, then `bootstrap/scss/bootstrap`, then `theme/_index.scss` with its partials), all by `@import`, so a project sets own variables before it. It is not part of `compostrap.scss`; the other modules keep working with plain Bootstrap (the colored ones take `--theme-*` tokens from the theme, with fallbacks to Bootstrap tokens).
- `src/scss/_variables.scss`: settings shared by modules (sidebar width, navbar height, menu sizes, nanobar height, icon font and glyphs of the arrows).
- `src/js/`: one file per module with JavaScript (`sidebar.js`, `sidebar-menu.js`, `theme-switcher.js`, `tooltip.js`, `dropzone.js`, `lightbox.js`, `strength.js`, `password-toggle.js`, `number-input.js`, `otp-input.js`, `selection.js`, `sortable.js`, `spinner.js`, `dialogs.js`, `datepicker.js`, `chart.js`), `index.js` exports all of them except `Datepicker` and `Charts` (they need the optional `vanilla-calendar-pro` and `chart.js`, so they are imported from `compostrap/datepicker` and `compostrap/chart` only) plus `SidebarSkeleton` and `SidebarMenuApp` (the initializers of the old packages).
- `src/illustrations/`: SVG illustrations of the module `empty`, exported as `compostrap/illustrations/*`.
- `scripts/build-css.js` compiles every entry point to `dist/css/`, `vite build` the JavaScript to `dist/js/`. `dist/` is not versioned, `prepublishOnly` builds it.
- `demo/`: sources of the demo pages. `scripts/build-demo.js` (`npm run demo`, run by `npm run dev`) fills `demo/_layout.html` (the shell: sidebar, navbar, footer, scripts) with each `demo/pages/<file>` and writes `<file>` to the root; a page source holds only its content boxes, a line `<!-- overlays -->` starts its offcanvases, modals and scripts, `demo/_shared-overlays.html` holds the modals of all pages, `demo/img/` own drawings (the shop products, the blog, the gallery `gallery-*.svg`, the avatar; never photos of others and no outside image service: picsum.photos was replaced, it is often down). A menu item with `layout` is filled into `demo/_layout-<layout>.html` instead (`auth`: the sign-in shell; `error`: a page of its own), an item with `items` is a submenu (open on its pages, its title in the breadcrumb), `new: true` shows a New badge (one item as a sample), `badge` a count, `hidden: true` builds the page without an item in the menu (the article of the blog, opened from the list of articles). Menu sections: Overview (dashboard), Bootstrap (typography, buttons, badges, forms, tables, navigation, overlays), Compostrap (elements, empty & loading, inputs), Modules (datagrid, gallery, sortable, Commerce › Products) and Pages (sign-in, sign-up, password recovery, account, permissions, Shop › products, product detail, cart, delivery and payment, customer information, order summary, order confirmation, cart and form states [layout `shop`: the storefront shell], Blog › articles, article [layout `blog`: the website shell], Errors › 404/403/500/maintenance). Edit the sources, never the generated root pages. Pages copy the markup of the drago templates, so the look can be tried before drago switches; every page section is a `content-box` with its heading inside (`header.mb-4.pb-2.border-bottom`, `h1.h5`, a subtitle).

## Rules

- Class names, CSS variables, `data-*` attributes and the JavaScript API are the public API: projects copy the markup, so a rename is a major version (before the first release they may still change).
- Module order: `theme` (or Bootstrap) first, then `theme-switcher`, `tooltip`, `elements`, `dialogs`, `settings`, `datagrid`, `selection`, `sortable`, `number-input`, `otp-input`, `datepicker`, `rating`, `chart`, `gallery`, `dropzone`, `lightbox`, `strength`, `password-toggle`, `empty`, `spinner`, `auth`, `shop`, `blog`, `sidebar`, `sidebar-menu`, `dashboard`; the layout comes last and finishes the earlier ones.
- A refactoring must not change the look: compare screenshots of all demo pages before and after (with animations off).
- Shadows of the surfaces on the page (boxes, cards, the sidebar and its panel, tiles, the sign-in box) and the scroll shadow of the white navbar come from `$soft-shadow` and `$navbar-scroll-shadow` in `_variables.scss` (and `$box-shadow-sm` of the theme); the user is trying looks without them, so they are `none` now (the last values are kept in the comment). A symmetric shadow drew a seam where the sidebar meets the navbar; a shadow, if any, falls right and down only. Floating parts (dropdowns, modals, offcanvas, the calendar, tooltips) and the raised active tab of a segmented control keep theirs.
- A faint line around the boxes of the page (content boxes, cards, the sign-in box, the boxes of the shop) is wired as `$surface-border` in `_variables.scss` and in `theme/_variables.scss` (cards); it is `none` now, the user tried `1px solid rgba(var(--bs-body-color-rgb), .07)` (.06 was too weak, .08 too strong) and has not decided. Do not turn it on or remove the wiring without being asked; a new box of the page takes `border: var.$surface-border` like the others. The sidebar, the navbar, tinted tiles and cards inside a modal or an offcanvas have no such line.
- Text is at least 14px (the body size). `$small-font-size: 1em` in the theme makes `small`, `.small`, form texts, feedback and the footer of a quote 14px; badges are 12px (`$badge-font-size: .75rem`, the least of Bootstrap 6). Smaller only where it is meant: `-sm`/`-xs` sizes (buttons, form controls, pagination, `badge-sm`), uppercase labels (table heads, menu section titles), tooltips, avatar initials, weekday letters of the calendar, the file extension chip of the gallery, `code`/`kbd`, chart axis scales (12px). On iOS only (`@supports (-webkit-touch-callout: none)` in `theme/_forms.scss` and `number-input`) the text of a field is 16px, also in the small size, because Safari zooms the page in on the focus of a field with a smaller text; the line height is set so the field keeps its height (36/30px). A new field with its own font size needs the same rule. Check a change with a measurement of the computed font sizes of all demo pages (scratchpad fonts.cjs pattern).
- Focus: a click with the mouse leaves no ring around buttons, checks, radios, switches, pages of a paginator, accordion headers or the number input (their ring is only for the keyboard, `:focus-visible`); a text field and a select keep the thin ring and tinted border on focus, as it shows where the typing goes. Check a change by clicking each kind of control and reading its computed `box-shadow` (scratchpad sweep.cjs pattern).
- No animation on hover anywhere: a hovered row, link, button, tab or tile changes its background and color at once (no `transition` of background-color/color; `$btn-transition`, `$nav-link-transition`, `$pagination-transition` are null in the theme, the accordion keeps only its corners). Transitions stay only for movement and states that are not hover (sidebar slide, arrow rotation, strength meter, switch knob, loading ring).
- Colors come from Bootstrap tokens (`var(--bs-*)`, `rgba(var(--bs-body-color-rgb), …)`, `color-mix()`) so both themes work without separate light/dark values; no `darken()`/`lighten()` (use `sass:color`). The user dislikes borders: cards, boxes, alerts, dropdowns and modals lift by soft shadows or tints.
- The look follows Bootstrap 6 on plain Bootstrap 5, with muted shades and a denser typography: 14px text, headings 600 in the scale h1 28, h2 24, h3 21, h4 19, h5 18 px (`h5` heads pages and boxes; the subtitle in a box header is 14px, not small), controls 36/30/44px; the menu has 44px rows, uppercase section titles at 60 %, links at 85 %, Bootstrap Icons chevrons at 85 % with a .4px stroke that rotate when a submenu opens, and pills (current page on any level, hover a slightly weaker pill `--sm-pill-hover-bg`, no animation). Sizes are Sass variables.
- Colors of Bootstrap 6 (hex in `theme/_variables.scss`, tints mixed in oklch from `$theme-color-sources`, needs Dart Sass 1.79+) and its color API: `.theme-*` contexts with `--theme-*` tokens (also set by `.btn-{color}`, `.btn-outline-{color}`, `.alert-{color}`), badges `.badge-subtle`/`.badge-outline`, buttons `.btn-solid`/`.btn-outline`/`.btn-subtle`/`.btn-text`; keep the names equal to Bootstrap 6. Secondary is a light gray, one for the solid and the subtle button and the gray subtle badge (`$theme-secondary-bg` #f0f0f0 in `theme/_colors.scss`; user's choice: `$gray-100` was a hair too light), with one hover for all gray buttons and the badge (half way to `$gray-200`, about #ebebeb; the 5 % darkening of the solid colors was a hair too much) and `$gray-200` for a press; the dark theme does the same with `$theme-secondary-bg-dark` #363636 (the lightest gray on which the gray text of a subtle badge reads 4.5:1) and `$gray-700` for a press; outline light takes the hover and pressed fill of the solid button. Solid info is cyan darkened by 14 % (`$theme-solid-shades`) with white text instead of the dark text of Bootstrap 6. White text on the solid colors stays under 4.5:1 (primary 3.78, success 3.03, info 3.79, danger 4.42; Lighthouse flags it): darkening them for 4.5:1 (primary 8 %, success 16 %, info 21 %, danger 2 %) was tried and rejected by the user, the colors were too dark. Solid warning keeps the yellow, its text is the yellow mixed with 54 % black (`$theme-contrast-weights`, a hair darker than the brown of the hovered subtle button, about 6:1; user's wish: the near black of Bootstrap was too loud). Text colors (fg) reach 4.5:1 on their own tint (`$theme-fg-weights`: success 24 %, info 29 %, warning 40 %, others 16 %); measure the contrast when a color changes. A green text on a light surface (`.text-success`, the text of a valid field) is `$success-text` (the green darkened by 16 %, the least for 4.5:1 on white; the user wants no darker), the dark theme keeps the green; the shop writes the primary color on its tint as `--shop-primary-text` (darkened by 18 %, light theme only). `btn-subtle`/`btn-text` take the theme focus ring (`--bs-focus-ring-*`). Badge corners stay Bootstrap 5 (the small menu badges are `badge-sm rounded-pill`).
- Forms and navs of Bootstrap 6 on the markup of Bootstrap 5: 20px checks and radios, a 35 × 20px switch with a white knob on a gray track (Bootstrap 6 has its own `.switch` markup, not copied); tabs and pills with a 2px gap, gray links, a light background on hover, a faint frame on a hovered tab; the accordion opens with a light gray header (border color mixed into the surface), text and chevron in the body color, no focus ring on click (only `:focus-visible`). Checks, radios and switches have a small size `form-check-sm` (16px, a 28 × 16px switch; on the `.form-check` wrapper or on a check without one; user's wish, the default stays 20px).
- An icon or a unit of a field stands inside it, not in an input group (user's wish: "nicer and more modern"): the form adorn of Bootstrap 6 with its names and markup, `label.form-control.form-adorn` (`.form-adorn-end` for the end) with a `.form-adorn-icon` or `.form-adorn-text` (`aria-hidden`) and an `input.form-ghost`; the wrapper takes the focus look of a field by `:focus-within`, sizes are `form-control-sm`/`-lg` on it; icons are the icon font (Bootstrap 6 uses SVG, both work). An input group stays only where a button or a select joins a field (a label must not hold interactive content): the cross of a datagrid filter, a select with an add button. A datepicker field needs no adornment, it has its calendar icon.
- Buttons of a form or a confirmation stand in one order everywhere (user's rule): Cancel first, the main action last (Cancel, Save; Cancel, Delete), aligned right (`justify-content-end`, `.modal-footer`, `.offcanvas-actions` in an offcanvas, a `.card-footer` with `justify-content-end`); the confirmation over a gallery tile is centered but keeps the order.
- Dropdown items are pills like the links of the sidebar menu (user's wish: the hover went over the whole width): the menu has `$dropdown-padding-x: .5rem`, items `$dropdown-item-padding-x: .5rem` (the text stays 1rem from the edge), rounded by `$dropdown-item-border-radius` with a 2px gap between them, dividers over the whole width; the compact sidebar menu does the same.
- Overlays: every `.offcanvas-start/-end/-top/-bottom` floats (also the responsive `.offcanvas-lg`… below their breakpoint; margin `--cs-offcanvas-margin`, radius, shadow, no border, an extra `translate` so a closed panel leaves the window; `.offcanvas-flush` opts out); the header of an offcanvas and of a modal is tinted over the whole width (`$gray-100` in the light theme, a shade darker than the tertiary background at the user's wish; `--bs-tertiary-bg` in the dark one) with no line under it (user's choice after a trial of a line from the title to the close button: on the dark theme it read as a divider of the form); the modal footer has no line (the line over the whole width above it was ugly, user's wish); tabs in an offcanvas header (`.offcanvas-header > .btn-group[role=tablist]`) move to their own row below 768px. Modals have no border and a shadow; `dialogs` adds `.modal-status` and `.modal-confirm` (they replace the colored danger header of the drago `@modal.latte`) and `.offcanvas-actions` (the sticky footer inline style of blog/commerce/static-page).
- The theme switch lives in the user menu (user's choice over an icon in the navbar): a segmented control light / dark / auto (`data-theme-value`, `.dropdown-theme` in `dashboard`, the menu with `data-bs-auto-close="outside"`); `auto` follows the system and its changes and is the default until a user chooses (`defaultTheme`); its button tells the theme of the system in its `title`. The inline head script of every layout resolves `auto` (stored or not) before the page is drawn. A choice made in another tab is taken over (the `storage` event). The single toggle `[data-theme-switcher]` stays for the sign-in pages; a toggle to the theme of the system stores `auto`, so the page is not pinned against a later change of the system.
- The fixed part of the sidebar with a brand is a flex column of the window height (brand, then the menu fills the rest, 2rem room at its end); a fixed `calc(100vh - top)` cut the last links off once the brand got taller. A link that only opens a submenu has no `href` (the browser showed "…#" in its status bar over the last links); `SidebarMenu` makes it `role=button`, `tabindex=0` and opens it by Enter/Space.
- The first state of the menu is drawn by CSS from the server markup, not by `SidebarMenu`: the arrow of `.link-arrow` (right, down with `.link-current`) and the open submenu of the current group (`.link-current + .list-hidden`). The script adds `.up`/`.down` and an inline `display` only later (a deferred module), and an arrow drawn by it moved the badge of the group aside after the first paint, only sometimes (it depends on whether the script runs before the paint), seen on quick reloads; plain links never jumped. The JS keeps its classes, the inline `display: none` of a closed current group wins over the CSS.
- The compact sidebar (user's choice after a trial): from md up `html.sidebar-compact` narrows the sidebar to the icons of the first level (`$sm-compact-width` 4.5rem, styles in `sidebar-menu/_compact.scss`), switched by a `.navbar-icon` button with `bi-layout-sidebar` and `data-sidebar-compact` at the left of the navbar (before the breadcrumb, md up only), remembered in `localStorage` (`sidebar-compact`) and set before the page is drawn by an inline head script of the layout; `Sidebar` (in `sidebar.js`, run by `Sidebar.init()`) does the switching. The texts stay in the page (`font-size: 0`, read by screen readers), section titles become short lines, badges and submenus are hidden. The name of a hovered link is a label in the colors of the default tooltip, a box of its own at the end of `<body>` (the scrolling menu would cut it off). A link with a submenu does not widen the sidebar (user's wish: it was tried and disliked): it opens its links in a `.sidebar-compact-menu` next to the icon (`.sidebar-compact-menu-header` with the group name, `.sidebar-compact-menu-item` links, the current page `active`), also at the end of `<body>`; it closes by another click on the icon, outside, Esc, a scroll or a resize, and works by the keyboard like a dropdown (Tab after its last link goes on from the icon). It has the look of the dropdowns from the Sass variables of the theme but deliberately not the class `.dropdown-menu`: Bootstrap handles the keys of every `.dropdown-menu` on the document and opened the first dropdown of the page by the arrows. `SidebarMenu` leaves a click on a group alone in the compact sidebar (its own `_isCompact()`, the same test as `Sidebar.isCompact()`), so the submenu in the wide sidebar keeps its state. Known shortcuts kept on purpose: the text of a link is hidden by `font-size: 0` (the menu markup has a bare text node next to the icon; a `<span>` around it would be cleaner, but the markup is copied by drago), the submenus need `display: none !important` (SidebarMenu opens them by an inline style), a resize event is dispatched after a switch so Perfect scrollbar measures again.
- `tooltip` is the CSS tooltip of drago-ex/component (`data-tooltip` + `aria-label`); the pseudo-element gets its `content` only on hover/focus and fades in by a keyframe, because a hidden one widened the scroll area of a table-responsive; variants `left`, `end`, `start`, `bottom`; `data-tooltip-wrap` lets a long text (a list) wrap within 22rem and keeps the line breaks of its `aria-label` (`white-space: pre-line`); the default is `$gray-600` with white text in the light theme (user's choice over the black of the text) and the light text color in the dark one; `data-tooltip-color` colors it (info has white text on the cyan darkened by 14 % like the solid info of the theme, user's wish; warning has the brown text of the solid warning button, the yellow mixed with 54 % black, user's wish; light keeps dark text); a button with an open dropdown (`aria-expanded=true`) hides its tooltip. The optional script `CssTooltip` (`tooltip.js`; not `Tooltip`, the name of Bootstrap) adds Esc: it sets `data-tooltip-hidden` on the element whose tooltip is shown, until the mouse and the focus leave it, and stops the key, so a dialog under it stays open. The tooltip is deliberately not hoverable (`pointer-events: none`): a tooltip that takes the mouse would cover the next button of a row of icon buttons.
- `elements`: `.status-dot` (the bell of notifications instead of a number), `.stat-tile` (instead of @tile.latte of commerce; two per row on phones), `.list-row`, `.datagrid-filter-clear` (the cross of an active datagrid filter), and the loading state `[aria-busy=true]` on `.content-box`, `.card` or `[data-loading-area]`, meant to be set by a Naja extension in drago.
- `settings`: `.nav-list` (`.nav-list-box` in a box of the tertiary color, the current link in the surface color), `.setting-row` with `.setting-row-control` (least width, so the texts line up), `.setting-list` (max width on wide screens) and `.setting-row-locked` (a lock for an inherited privilege instead of a disabled switch). The drago permissions page is their first user.
- `datagrid` rows are at least 2.375rem (38px, a row with a subtle badge; user's wish: the same spacing in every grid); a link in a cell is an `a.badge`, not a `btn-xs` (24px, it made the rows of the articles 2px higher).
- `datagrid` holds the styles of the table drago-ex/datagrid prints (it replaces `datagrid.scss` of that package, so the names are its names): `.datagrid-table` on the surface of its box, `.datagrid-filter-row` with `.datagrid-control` fields (not uppercase like the table head), `.datagrid-toolbar` and `.datagrid-filter` for the filters over the table, `.datagrid-row-clickable`, the narrow `.datagrid-actions` column and `.datagrid-actions-autohide` (row actions only under the mouse, with the focus in the row or an open menu; at once, no fade; always shown on a touch screen). `.datagrid-state` is a state with more than two values changed in a cell (user's wish: Published, Draft, Waiting): the subtle badge of the state is a `button` with a small `bi-chevron-down` that opens a dropdown with the states, the current one `active` (the theme styles `button.badge` like `a.badge`). `.datagrid-switch` is a switch of a state in a cell (user's choice over two bulk actions Publish and Unpublish, like the switches of the permissions page) and `.datagrid-control-range` the field of a date range filter, whose wrapper keeps room for two dates. The cross of a filter stays in `elements` (`_datagrid-filter.scss`). It has no JavaScript and no demo page of its own: the datagrid page of the demo shows it.
- `selection` is the bulk actions of a datagrid: checkboxes in a `.selection-cell` column (`data-selection-all`, `data-selection-item`) inside a `data-selection` wrapper and `.selection-bar` with the count and the actions, hidden until a row is chosen. The bar is sticky at the bottom of its box (it floats over the bottom edge of the window while the table is on the screen and never covers another box), as wide as its content, a floating surface with the shadow of the dropdowns (a lighter surface in dark). `RowSelection` works by event delegation like `lightbox` (`update()` after an AJAX redraw); a chosen row gets `table-active` of Bootstrap. A button of the bar with `data-selection-single` is an action for one row (Edit), disabled while more rows are chosen; `data-selection-rows` on the wrapper lets a click anywhere on a row choose it (user's wish for drago: one row is chosen without aiming at its checkbox), except a click on a link, a button, a field or a label, a click in a cell that holds a button (the rule of the row click and the menu of three dots) and the end of selecting a text. The datagrid of the demo is its first user; drago DataGrid.latte prints the same markup.
- A click outside does not close a modal or an offcanvas (user's rule: a dialog with a form must not vanish by a slip of the mouse; it closes by its cross, its Cancel button and Esc): `Dialogs.init()` (`src/js/dialogs.js`, module `dialogs`) sets the default `backdrop` of `bootstrap.Modal` and `bootstrap.Offcanvas` to `static` (Bootstrap from `window.bootstrap` or passed in), so it holds for dialogs of AJAX snippets and of scripts too. A dialog without a button to close it opts out by `data-bs-backdrop="true"` (the search). Only the administration layout of the demo calls it; the filters of the shop keep closing by a tap outside.
- Accessibility of the copied markup (from the review against modern-web-guidance; drago should print the same): a field with `is-invalid` has `aria-invalid="true"` and `aria-describedby` with the id of its `invalid-feedback`; the fields of an address have `autocomplete` tokens (`shop-customer.html`), required fields `required`; the `.toast-container` is `role="region"` with an `aria-label`. The sidebar below md is `inert` while closed (it only stands outside the window), takes the focus when opened and closes when the focus leaves it (`Sidebar.init()`); the page under it is deliberately not made inert, because the sidebar has no close button of its own and a screen reader must reach the toggle.
- Toasts: the theme draws `.toast` like the modals (no border, opaque surface, larger corners, the large shadow, a lighter surface in dark); `dialogs` adds `.toast-status`, the message of a state (a flash message of Nette) in the look of `.modal-confirm` (user's wish: "in the style of the modals"): the colored line of `.modal-status` at the top, an icon in `--theme-fg`, a title and a quiet text, colored by a `.theme-*` class. They stand in a `.toast-container.position-fixed.bottom-0.end-0` of the frame (in the demo in `_shared-overlays.html`, shown by buttons with `data-demo-toast`); showing and hiding is `bootstrap.Toast`, compostrap has no script for it (drago shows them from a Naja extension).
- Search: a `.navbar-icon` button with `bi-search` and the text Search from lg up (before the bell, like Notifications) opens `.modal-search` of `dialogs`: a field without a frame and without a focus ring at the top (the only field of the dialog), the results as `.list-row` links in groups with `.modal-search-title`, `.modal-search-empty` when nothing is found. A dialog was chosen over a field in the navbar, so the tuned navbar stays as it is and a phone gets the same search. The user doubts an administration needs it, so it is an optional part: compostrap only styles it, the results come from the server; in the demo Ctrl+K opens it and the field filters sample rows (demo script in `_layout.html`).

## Commands

- `npm run dev`: builds the demo pages and serves them.
- `npm run demo`: only builds the demo pages from `demo/`.
- `npm run build`: JavaScript and CSS into `dist/`.
- The public demo (`https://compostrap.github.io/demo/`) is built in the repository `compostrap.github.io` by its `npm run build:demo`: it takes this package from `../compostrap`, builds the demo pages by Vite into its `demo/` (classic scripts of `node_modules` go to `demo/lib/`, `demo/img` is copied) and the result is committed there. The demos of the old packages in its root stay as they are.
- `npm test`: smoke tests of the demo pages in Playwright (`tests/`, `playwright.config.js`; the browser once by `npx playwright install chromium`). It builds the demo and serves it by Vite on its own port. `pages.spec.js` opens every page of `demo/pages` (no error in the console, no failed request, nothing wider than the window), `sidebar.spec.js` and `components.spec.js` try the behavior of the JavaScript modules on the demo markup. They test behavior, not the look (screenshots stay a check by hand); outside photos are stubbed in `tests/fixtures.js`. A new module with JavaScript gets a test there, a change of the public markup or API updates its test.
