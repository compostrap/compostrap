# compostrap

One npm package for Bootstrap 5.3, independent of Nette and drago (drago packages use it, it never refers to them), for administrations and websites. It replaces the separate packages `theme-switcher-compostrap`, `sidebar-skeleton-compostrap`, `sidebar-menu-compostrap`, `sidebar-menu-2-compostrap` and `dashboard-skeleton-compostrap`; the pill look of `sidebar-menu-2` is part of `sidebar-menu` (`_pills.scss`), there is no flat menu.

## Architecture

Three layers; keep every new piece in the layer it belongs to:

| Layer | Modules | What belongs there |
|-------|---------|--------------------|
| Theme | `theme` | Bootstrap itself: its variables (`theme/_variables.scss`) and CSS that changes its components, plus the classes of Bootstrap 6 backported with their names (`theme-*` tokens, `btn-subtle`, `badge-subtle`, `breadcrumb-link`, `avatar`, `btn-xs`, `btn-icon`, `form-adorn`, `form-ghost`…). No own class names, except size modifiers in the naming of Bootstrap (`badge-sm`, `form-check-sm`) and `btn-group-segmented` (the look of `btn-group[role=tablist]` for any group). |
| Layout | `sidebar`, `sidebar-menu`, `dashboard` | the frame of an administration: sidebar, menu, navbar over the content (`navbar-*`), content boxes (`content-box`), page colors (`--ds-*`), nanobar. |
| Components | `theme-switcher`, `tooltip`, `elements`, `dialogs`, `settings`, `selection`, `number-input`, `datepicker`, `rating`, `chart`, `gallery`, `dropzone`, `lightbox`, `strength`, `password-toggle`, `empty`, `auth`, `shop`, `blog` | everything with an own name; the class prefix is the module or its part (`gallery-*`, `empty-*`, `auth-*`, `shop-*`, `blog-*`, `stat-*`, `setting-*`, `selection-*`). |

Where new code goes:
- It changes or completes a class of Bootstrap 5 or 6 → the theme, into the partial of that component (`theme/_buttons.scss`, `_badges`, `_alerts`, `_forms`, `_navs`, `_breadcrumb`, `_tables`, `_cards`, `_accordion`, `_overlays`, `_avatar`; colors and the `--theme-*` tokens in `_colors`, the page in `_base`). A new component of Bootstrap gets its own partial, imported in `theme/_index.scss`.
- It has an own name → a component module. A small piece of a page goes to `elements` (as its own partial), a piece of modals/offcanvas/toasts to `dialogs`, a section list or a setting row to `settings`; a bigger thing with its own markup or JavaScript gets a new module.
- It is a part of the frame of the administration → `sidebar`, `sidebar-menu` or `dashboard`.
- A component never goes into `dashboard` because it is first used on the dashboard; `dashboard` holds only the frame.

A new module:
1. `src/scss/<module>/_index.scss` (with partials for its parts) and the entry point `src/scss/<module>.scss` (`@use '<module>/index';`).
2. Load it in `src/scss/compostrap.scss` and list it in `scripts/build-css.js`, both in the module order below.
3. JavaScript (when it has any): `src/js/<module>.js`, export it in `src/js/index.js`, an entry in `vite.config.js` and in `exports` of `package.json` (`compostrap/<module>`).
4. A demo page (or a section of one) in `demo/pages/` and its item in the menu of `scripts/build-demo.js`.
5. Its description in `docs/<module>.md` (a part of the theme in `docs/theme.md`, of the frame in `docs/layout.md`), a row in the module table of `readme.md` with a link to it and its link in the Documentation list there. `readme.md` holds only the overview (requirements, installation, architecture, usage, light and dark theme, demo, tests); the markup, classes, variables and JavaScript of a module are described in `docs/`, one file per component.

## Files

- `src/scss/_bootstrap.scss`: the only place that loads Bootstrap (functions, variables, mixins) by `@import`, because Bootstrap 5.3 has no Sass modules, with `theme/_variables.scss` first; modules use it as `@use '../bootstrap' as bs;`. Everything else uses `@use`.
- `theme` is the exception among modules: `theme.scss` builds Bootstrap itself (`theme/_variables.scss` = Bootstrap variables with `!default`, then `bootstrap/scss/bootstrap`, then `theme/_index.scss` with its partials), all by `@import`, so a project sets own variables before it. It is not part of `compostrap.scss`; the other modules keep working with plain Bootstrap (the colored ones take `--theme-*` tokens from the theme, with fallbacks to Bootstrap tokens).
- `src/scss/_variables.scss`: settings shared by modules (sidebar width, navbar height, menu sizes, nanobar height, icon font and glyphs of the arrows).
- `src/js/`: one file per module with JavaScript (`sidebar.js`, `sidebar-menu.js`, `theme-switcher.js`, `dropzone.js`, `lightbox.js`, `strength.js`, `password-toggle.js`, `number-input.js`, `selection.js`, `datepicker.js`, `chart.js`), `index.js` exports all of them except `Datepicker` and `Charts` (they need the optional `vanilla-calendar-pro` and `chart.js`, so they are imported from `compostrap/datepicker` and `compostrap/chart` only) plus `SidebarSkeleton` and `SidebarMenuApp` (the initializers of the old packages).
- `src/illustrations/`: SVG illustrations of the module `empty`, exported as `compostrap/illustrations/*`.
- `scripts/build-css.js` compiles every entry point to `dist/css/`, `vite build` the JavaScript to `dist/js/`. `dist/` is not versioned, `prepublishOnly` builds it.
- `demo/`: sources of the demo pages. `scripts/build-demo.js` (`npm run demo`, run by `npm run dev`) fills `demo/_layout.html` (the shell: sidebar, navbar, footer, scripts) with each `demo/pages/<file>` and writes `<file>` to the root; a page source holds only its content boxes, a line `<!-- overlays -->` starts its offcanvases, modals and scripts, `demo/_shared-overlays.html` holds the modals of all pages, `demo/img/` own drawings of the shop products (never photos of other shops). A menu item with `layout` is filled into `demo/_layout-<layout>.html` instead (`auth`: the sign-in shell; `error`: a page of its own), an item with `items` is a submenu (open on its pages, its title in the breadcrumb), `new: true` shows a New badge (one item as a sample), `badge` a count, `hidden: true` builds the page without an item in the menu (the article of the blog, opened from the list of articles). Menu sections: Overview (dashboard), Bootstrap (typography, buttons, badges, forms, tables, navigation, overlays), Compostrap (elements, empty & loading, inputs), Modules (datagrid, gallery, Commerce › Products) and Pages (sign-in, sign-up, password recovery, account, permissions, Shop › products, product detail, cart, delivery and payment, customer information, order summary, order confirmation, cart and form states [layout `shop`: the storefront shell], Blog › articles, article [layout `blog`: the website shell], Errors › 404/403/500/maintenance). Edit the sources, never the generated root pages. Pages copy the markup of the drago templates, so the look can be tried before drago switches; every page section is a `content-box` with its heading inside (`header.mb-4.pb-2.border-bottom`, `h1.h5`, a subtitle).

## Rules

- Class names, CSS variables, `data-*` attributes and the JavaScript API are the public API: projects copy the markup, so a rename is a major version (before the first release they may still change).
- Module order: `theme` (or Bootstrap) first, then `theme-switcher`, `tooltip`, `elements`, `dialogs`, `settings`, `selection`, `number-input`, `datepicker`, `rating`, `chart`, `gallery`, `dropzone`, `lightbox`, `strength`, `password-toggle`, `empty`, `auth`, `shop`, `blog`, `sidebar`, `sidebar-menu`, `dashboard`; the layout comes last and finishes the earlier ones.
- A refactoring must not change the look: compare screenshots of all demo pages before and after (with animations off; the photo tiles of picsum differ between runs).
- Shadows of the surfaces on the page (boxes, cards, the sidebar and its panel, tiles, the sign-in box) and the scroll shadow of the white navbar come from `$soft-shadow` and `$navbar-scroll-shadow` in `_variables.scss` (and `$box-shadow-sm` of the theme); the user is trying looks without them, so they are `none` now (the last values are kept in the comment). A symmetric shadow drew a seam where the sidebar meets the navbar; a shadow, if any, falls right and down only. Floating parts (dropdowns, modals, offcanvas, the calendar, tooltips) and the raised active tab of a segmented control keep theirs.
- A faint line around the boxes of the page (content boxes, cards, the sign-in box, the boxes of the shop) is wired as `$surface-border` in `_variables.scss` and in `theme/_variables.scss` (cards); it is `none` now, the user tried `1px solid rgba(var(--bs-body-color-rgb), .07)` (.06 was too weak, .08 too strong) and has not decided. Do not turn it on or remove the wiring without being asked; a new box of the page takes `border: var.$surface-border` like the others. The sidebar, the navbar, tinted tiles and cards inside a modal or an offcanvas have no such line.
- Text is at least 14px (the body size). `$small-font-size: 1em` in the theme makes `small`, `.small`, form texts, feedback and the footer of a quote 14px; badges are 12px (`$badge-font-size: .75rem`, the least of Bootstrap 6). Smaller only where it is meant: `-sm`/`-xs` sizes (buttons, form controls, pagination, `badge-sm`), uppercase labels (table heads, menu section titles), tooltips, avatar initials, weekday letters of the calendar, the file extension chip of the gallery, `code`/`kbd`, chart axis scales (12px). Check a change with a measurement of the computed font sizes of all demo pages (scratchpad fonts.cjs pattern).
- Focus: a click with the mouse leaves no ring around buttons, checks, radios, switches, pages of a paginator, accordion headers or the number input (their ring is only for the keyboard, `:focus-visible`); a text field and a select keep the thin ring and tinted border on focus, as it shows where the typing goes. Check a change by clicking each kind of control and reading its computed `box-shadow` (scratchpad sweep.cjs pattern).
- No animation on hover anywhere: a hovered row, link, button, tab or tile changes its background and color at once (no `transition` of background-color/color; `$btn-transition`, `$nav-link-transition`, `$pagination-transition` are null in the theme, the accordion keeps only its corners). Transitions stay only for movement and states that are not hover (sidebar slide, arrow rotation, strength meter, switch knob, loading ring).
- Colors come from Bootstrap tokens (`var(--bs-*)`, `rgba(var(--bs-body-color-rgb), …)`, `color-mix()`) so both themes work without separate light/dark values; no `darken()`/`lighten()` (use `sass:color`). The user dislikes borders: cards, boxes, alerts, dropdowns and modals lift by soft shadows or tints.
- The look follows Bootstrap 6 on plain Bootstrap 5, with muted shades and a denser typography: 14px text, headings 600 in the scale h1 28, h2 24, h3 21, h4 19, h5 18 px (`h5` heads pages and boxes; the subtitle in a box header is 14px, not small), controls 36/30/44px; the menu has 44px rows, uppercase section titles at 60 %, links at 85 %, Bootstrap Icons chevrons at 85 % with a .4px stroke that rotate when a submenu opens, and pills (current page on any level, hover a slightly weaker pill `--sm-pill-hover-bg`, no animation). Sizes are Sass variables.
- Colors of Bootstrap 6 (hex in `theme/_variables.scss`, tints mixed in oklch from `$theme-color-sources`, needs Dart Sass 1.79+) and its color API: `.theme-*` contexts with `--theme-*` tokens (also set by `.btn-{color}`, `.btn-outline-{color}`, `.alert-{color}`), badges `.badge-subtle`/`.badge-outline`, buttons `.btn-solid`/`.btn-outline`/`.btn-subtle`/`.btn-text`; keep the names equal to Bootstrap 6. Secondary is a light gray; outline secondary/light take the hover and pressed fill of the solid button (solid and outline look the same then). Solid info is cyan darkened by 14 % (`$theme-solid-shades`) with white text instead of the dark text of Bootstrap 6. Text colors (fg) reach 4.5:1 on their own tint (`$theme-fg-weights`: success 24 %, info 29 %, warning 40 %, others 16 %); measure the contrast when a color changes. A green text on a light surface (`.text-success`, the text of a valid field) is `$success-text` (the green darkened by 16 %, the least for 4.5:1 on white; the user wants no darker), the dark theme keeps the green; the shop writes the primary color on its tint as `--shop-primary-text` (darkened by 18 %, light theme only). `btn-subtle`/`btn-text` take the theme focus ring (`--bs-focus-ring-*`). Badge corners stay Bootstrap 5 (the small menu badges are `badge-sm rounded-pill`).
- Forms and navs of Bootstrap 6 on the markup of Bootstrap 5: 20px checks and radios, a 35 × 20px switch with a white knob on a gray track (Bootstrap 6 has its own `.switch` markup, not copied); tabs and pills with a 2px gap, gray links, a light background on hover, a faint frame on a hovered tab; the accordion opens with a light gray header (border color mixed into the surface), text and chevron in the body color, no focus ring on click (only `:focus-visible`). Checks, radios and switches have a small size `form-check-sm` (16px, a 28 × 16px switch; on the `.form-check` wrapper or on a check without one; user's wish, the default stays 20px).
- An icon or a unit of a field stands inside it, not in an input group (user's wish: "nicer and more modern"): the form adorn of Bootstrap 6 with its names and markup, `label.form-control.form-adorn` (`.form-adorn-end` for the end) with a `.form-adorn-icon` or `.form-adorn-text` (`aria-hidden`) and an `input.form-ghost`; the wrapper takes the focus look of a field by `:focus-within`, sizes are `form-control-sm`/`-lg` on it; icons are the icon font (Bootstrap 6 uses SVG, both work). An input group stays only where a button or a select joins a field (a label must not hold interactive content): the cross of a datagrid filter, a select with an add button. A datepicker field needs no adornment, it has its calendar icon.
- Buttons of a form or a confirmation stand in one order everywhere (user's rule): Cancel first, the main action last (Cancel, Save; Cancel, Delete), aligned right (`justify-content-end`, `.modal-footer`, `.offcanvas-actions` in an offcanvas, a `.card-footer` with `justify-content-end`); the confirmation over a gallery tile is centered but keeps the order.
- Overlays: every `.offcanvas-start/-end/-top/-bottom` floats (also the responsive `.offcanvas-lg`… below their breakpoint; margin `--cs-offcanvas-margin`, radius, shadow, no border, an extra `translate` so a closed panel leaves the window; `.offcanvas-flush` opts out); tabs in an offcanvas header (`.offcanvas-header > .btn-group[role=tablist]`) move to their own row below 768px. Modals have no border and a shadow; `dialogs` adds `.modal-status` and `.modal-confirm` (they replace the colored danger header of the drago `@modal.latte`) and `.offcanvas-actions` (the sticky footer inline style of blog/commerce/static-page).
- The theme switch lives in the user menu (user's choice over an icon in the navbar): a segmented control light / dark / auto (`data-theme-value`, `.dropdown-theme` in `dashboard`, the menu with `data-bs-auto-close="outside"`); `auto` follows the system and its changes. The inline head script of every layout resolves a stored `auto` before the page is drawn. The single toggle `[data-theme-switcher]` stays for the sign-in pages.
- The fixed part of the sidebar with a brand is a flex column of the window height (brand, then the menu fills the rest, 2rem room at its end); a fixed `calc(100vh - top)` cut the last links off once the brand got taller. A link that only opens a submenu has no `href` (the browser showed "…#" in its status bar over the last links); `SidebarMenu` makes it `role=button`, `tabindex=0` and opens it by Enter/Space.
- The compact sidebar (user's choice after a trial): from md up `html.sidebar-compact` narrows the sidebar to the icons of the first level (`$sm-compact-width` 4.5rem, styles in `sidebar-menu/_compact.scss`), switched by a `.navbar-icon` button with `bi-layout-sidebar` and `data-sidebar-compact` at the left of the navbar (before the breadcrumb, md up only), remembered in `localStorage` (`sidebar-compact`) and set before the page is drawn by an inline head script of the layout; `Sidebar` (in `sidebar.js`, run by `Sidebar.init()`) does the switching. The texts stay in the page (`font-size: 0`, read by screen readers), section titles become short lines, badges and submenus are hidden. The name of a hovered link is a label in the colors of the default tooltip, a box of its own at the end of `<body>` (the scrolling menu would cut it off). A link with a submenu does not widen the sidebar (user's wish: it was tried and disliked): it opens its links in a `.sidebar-compact-menu` next to the icon (`.sidebar-compact-menu-header` with the group name, `.sidebar-compact-menu-item` links, the current page `active`), also at the end of `<body>`; it closes by another click on the icon, outside, Esc, a scroll or a resize, and works by the keyboard like a dropdown (Tab after its last link goes on from the icon). It has the look of the dropdowns from the Sass variables of the theme but deliberately not the class `.dropdown-menu`: Bootstrap handles the keys of every `.dropdown-menu` on the document and opened the first dropdown of the page by the arrows. `SidebarMenu` leaves a click on a group alone in the compact sidebar (its own `_isCompact()`, the same test as `Sidebar.isCompact()`), so the submenu in the wide sidebar keeps its state. Known shortcuts kept on purpose: the text of a link is hidden by `font-size: 0` (the menu markup has a bare text node next to the icon; a `<span>` around it would be cleaner, but the markup is copied by drago), the submenus need `display: none !important` (SidebarMenu opens them by an inline style), a resize event is dispatched after a switch so Perfect scrollbar measures again.
- `tooltip` is the CSS tooltip of drago-ex/component (`data-tooltip` + `aria-label`); the pseudo-element gets its `content` only on hover/focus and fades in by a keyframe, because a hidden one widened the scroll area of a table-responsive; variants `left`, `end`, `bottom`; the default is `$gray-600` with white text in the light theme (user's choice over the black of the text) and the light text color in the dark one; `data-tooltip-color` colors it (info has white text on the cyan darkened by 14 % like the solid info of the theme, user's wish; warning and light keep dark text); a button with an open dropdown (`aria-expanded=true`) hides its tooltip.
- `elements`: `.status-dot` (the bell of notifications instead of a number), `.stat-tile` (instead of @tile.latte of commerce; two per row on phones), `.list-row`, `.datagrid-filter-clear` (the cross of an active datagrid filter), and the loading state `[aria-busy=true]` on `.content-box`, `.card` or `[data-loading-area]`, meant to be set by a Naja extension in drago.
- `settings`: `.nav-list` (`.nav-list-box` in a box of the tertiary color, the current link in the surface color), `.setting-row` with `.setting-row-control` (least width, so the texts line up), `.setting-list` (max width on wide screens) and `.setting-row-locked` (a lock for an inherited privilege instead of a disabled switch). The drago permissions page is their first user.
- `selection` is the bulk actions of a datagrid: checkboxes in a `.selection-cell` column (`data-selection-all`, `data-selection-item`) inside a `data-selection` wrapper and `.selection-bar` with the count and the actions, hidden until a row is chosen. The bar is sticky at the bottom of its box (it floats over the bottom edge of the window while the table is on the screen and never covers another box), as wide as its content, a floating surface with the shadow of the dropdowns (a lighter surface in dark). `RowSelection` works by event delegation like `lightbox` (`update()` after an AJAX redraw); a chosen row gets `table-active` of Bootstrap. The datagrid of the demo is its first user; drago DataGrid.latte should print the same markup.
- Toasts: the theme draws `.toast` like the modals (no border, opaque surface, larger corners, the large shadow, a lighter surface in dark); `dialogs` adds `.toast-status`, the message of a state (a flash message of Nette) in the look of `.modal-confirm` (user's wish: "in the style of the modals"): the colored line of `.modal-status` at the top, an icon in `--theme-fg`, a title and a quiet text, colored by a `.theme-*` class. They stand in a `.toast-container.position-fixed.bottom-0.end-0` of the frame (in the demo in `_shared-overlays.html`, shown by buttons with `data-demo-toast`); showing and hiding is `bootstrap.Toast`, compostrap has no script for it (drago shows them from a Naja extension).
- Search: a `.navbar-icon` button with `bi-search` and the text Search from lg up (before the bell, like Notifications) opens `.modal-search` of `dialogs`: a field without a frame and without a focus ring at the top (the only field of the dialog), the results as `.list-row` links in groups with `.modal-search-title`, `.modal-search-empty` when nothing is found. A dialog was chosen over a field in the navbar, so the tuned navbar stays as it is and a phone gets the same search. The user doubts an administration needs it, so it is an optional part: compostrap only styles it, the results come from the server; in the demo Ctrl+K opens it and the field filters sample rows (demo script in `_layout.html`).
- The account page (`demo/pages/account.html`, the link Account of the user menu) copies drago `project-account` (profile information, change of the password) inside the administration: a box with the avatar, name, role and e-mail of the user, then the two forms in boxes next to each other from xl up, under each other below (the user allowed to replace the tabs of project-account; both forms are short, so nothing has to be hidden). It needs no styles of its own: `content-box`, `avatar-lg`, `password-toggle`, `strength`.
- `number-input` has no border and no box around the whole: two quiet gray square buttons (`rgba(body, .06)`, darker at once on hover, 32px, a step smaller than a form control by the user's wish; 26px sm, 38px lg) with the number between them on the surface, the field as wide as its number by `field-sizing: content`, a faint tint in the field while it is typed in (user's choice among the tried looks: first a gray track of `rgba(body, .05)` around all three with a raised hovered button, then the look of a bordered form field with the buttons inside, rejected: no border on it); a step fires input and change for an AJAX recount of a cart.
- `datepicker` follows the datepicker of Bootstrap 6: Vanilla Calendar Pro (optional peer, external in the build), the same data attributes, its styles moved to the tokens of Bootstrap 5 (no border, the shadow of the dropdowns, a lighter surface in dark, no muted weekends). Differences: the value is ISO by default (`data-bs-date-format="locale"` for display), because a server reads it. The calendar is created on the first focus; later focuses are opened by Vanilla Calendar Pro itself (`openOnFocus`), because it returns the focus to the input after a choice and an own focusin handler would reopen it. In a modal or an offcanvas the calendar (at the end of the body) keeps its `focusin` from the focus trap of Bootstrap, which took the focus back and closed it before a click reached a day. A field that opens the calendar shows a small gray calendar at its end (user's wish; a background image like the arrow of a select, `$datepicker-icon`, one gray for both themes), except a field of an input group (its icon is in the group) and a field with a validation icon.
- `chart` is Chart.js (MIT, optional peer, external in the build). ApexCharts was rejected: from version 5 its license forbids redistribution in toolkits and platforms used by others without a paid OEM license, which compostrap/drago are. Charts are markup (`canvas[data-chart]` with JSON), so Latte prints them; the colors are read from CSS tokens and resolved to plain rgb (a canvas takes no color-mix), redrawn on a change of `data-bs-theme`. The categorical palette `--chart-1…4` passed the validator of the dataviz skill (lightness band, chroma, CVD and normal-vision separation, 3:1 contrast) on the light and the dark surface; change it only with a new validation. Marks follow the dataviz rules: 2px lines, a 10 % area wash, columns ≤ 24px with 4px rounded ends, hairline grid without x lines, no animation, a crosshair and an HTML tooltip (value first), a legend from two series, direct values at the ends of ranked bars (`bar-horizontal`) instead of a value axis, a hidden table of the values, no donut (part-to-whole = ranked bars), one axis only.
- `rating` is CSS only: radio inputs and labels with a star mask, filling by `:has()`; `rating-static` is a gradient under a repeated star mask.
- `gallery` unifies the image tiles of project-gallery (`gallery-item`, `gallery-actions`, same names) and project-commerce (`commerce-photo*`, to be renamed; its open state is `gallery-actions show`, its main photo label `gallery-badge`).
- `dropzone` is a plain file input over a styled label (no Dropzone.js: it uploads by its own XHR and would bypass Nette forms, validation and Naja); `DropzoneInput` only toggles `is-dragover`, lists the chosen file names and submits the form with `data-dropzone-submit`.
- `lightbox` is own code on the native `<dialog>` (no library): one dialog created on first use, links found by event delegation (works for AJAX content), inline SVG icons, labels by `Lightbox.init({...})`.
- `strength` copies the strength component of Bootstrap 6 (classes `strength`, `strength-segment`, `strength-bar`, `strength-text`, attribute `data-bs-strength`, its scoring and thresholds), so drago markup stays when Bootstrap 6 comes; the script works by event delegation like `lightbox`.
- `password-toggle` is the password toggle of drago-ex/form (`@form-password.latte`, `PasswordToggle` of Naja) without Naja: `.password-toggle` around the input and a `button.password-toggle-btn[data-password-toggle]`; the script works by event delegation like `lightbox`, switches the type of the input and `aria-pressed`, and switches a shown password back when its form is sent. The icon is CSS only: glyphs of the icon font (`$icon-eye`, `$icon-eye-slash`) in the color of the text, chosen by the type of the input (masks were tried and looked ragged: a mask is blurred when the input stands between two pixels, e.g. on a centered page), the button is shown only after `init()` (`data-password-toggle` on `<html>`). The meter of `strength` stands under the wrapper and rates a shown password too. The sign-in, sign-up and recovery pages use it.
- `empty` holds empty states and error pages; the illustrations are own drawings (never copy illustrations of other products), every color is `style="fill|stroke: var(--cs-illustration-*, fallback)"` so an inlined SVG follows the theme and an `<img>` still has colors; keep the palette tokens in new ones. The demo pages inline them (regenerate when an SVG changes).
- `auth` is the sign-in shell (box in the middle, `auth-card-split` with a gray visual and a deeper gray icon, the languages next to the theme switch in `.auth-actions` of `.auth-top`: the same dropdown as in the navbar of the administration, a `navbar-icon` button with `bi-translate` and the code of the current language (user's choice over the plain links Čeština · English over the form; `.auth-toolbar` with such links stays as an optional part of the box).
- `shop` is the storefront of an e-shop outside the administration (its own shell `demo/_layout-shop.html`: a white header with the mini cart, the page in `--shop-page-bg`, boxes in `--shop-surface-bg`). The user tunes it by screenshots against Alza; these choices are his, keep them:
  - Everything on a page stands in a box, nothing hangs on the page background: no visible page heading on the product list (the `h1` is `visually-hidden`), no "back" link on the detail, a button always inside its box. The gap under the header is its own (1.5rem), boxes are 1rem apart.
  - The welcome band (`.shop-hero`, only on the product list) is the one thing outside a box: it belongs to the header, so it joins it without a gap in the whole width of the window (a box in the width of the content was tried: it read as one more box among the boxes, like an advertisement). It is low (about 80px), tinted with the primary color with a gradient towards the icons, and holds a title in two blues (a deeper one of its own, the primary one in `<em>`; a dark title was too loud), one line of text and five white icons of the icon font on round primary chips that grow stronger to the right. No label over the title (the name is in the logo), no button, no drawings of products and no cart icon in a circle (all tried and rejected). In the demo a page source puts it before a line `<!-- content -->`; `build-demo.js` fills that part into `{{hero}}` of the shop layout, between the header and `main`.

## Commands

- `npm run dev`: builds the demo pages and serves them.
- `npm run demo`: only builds the demo pages from `demo/`.
- `npm run build`: JavaScript and CSS into `dist/`.
- `npm test`: smoke tests of the demo pages in Playwright (`tests/`, `playwright.config.js`; the browser once by `npx playwright install chromium`). It builds the demo and serves it by Vite on its own port. `pages.spec.js` opens every page of `demo/pages` (no error in the console, no failed request, nothing wider than the window), `sidebar.spec.js` and `components.spec.js` try the behavior of the JavaScript modules on the demo markup. They test behavior, not the look (screenshots stay a check by hand); outside photos are stubbed in `tests/fixtures.js`. A new module with JavaScript gets a test there, a change of the public markup or API updates its test.
